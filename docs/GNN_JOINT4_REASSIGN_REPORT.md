## 1. 读代码后的两个关键实测（决定了实现方式）

1. 仓库现有原生协调评价 `priority_schedule()`（HGA/WAG 搜索期用的同一函数）在**有干涉**的 GNN 方案上直接返回 DEADLOCK：`validation_01` 的初解和 8 个候选**全部** native DEADLOCK（B32 却全部 FEASIBLE）。因此它不能当硬过滤。
2. 在**无干涉**排样上它与 B32 **逐位相等**：`validation_07` 的 8/9 个方案 native Cmax == B32 Cmax，native DEADLOCK 当且仅当 B32 DEADLOCK；单次 ~2ms（首次含 numba 编译）。

所以本轮把 native 用作「GNN 排序 + native 筛选」：origin 的 native 有限时按 native Cmax 排序；origin native 为 DEADLOCK 时只把 native 可行者前置、其余保持 GNN 顺序，且**永远不丢弃候选、不把 native 当可行性证明**。30 组 TRAIN 候选里 native 可行 158/282（56%），说明它在近半情况下可用。

## 2. 修改了哪些核心代码（全部在 `scripts/run_gnn_weld_layout.py`）

| 位置 | 改动 | 为什么 |
|---|---|---|
| `joint4_bottleneck_core()` | FEASIBLE 核心改为「瓶颈机器人转出 + 接收方父」：`critical = argmax B32 完成时间`，`peak = argmax P_r`；转出父按 `加工 + 0.5×(真实 critical WAIT/阻塞) + 0.25×MOVE` 排序；接收机器人取**完成时间不晚于 critical** 且能接收至少一个转出父的机器人（完成时间→负载→覆盖数）；接收方父按同一打分排序；q=4 时 2 转出 + 2 接收 | 旧 Joint3B 只在瓶颈机器人上取 3 个父，无法表达“转出+接收交换”；HGA M1/M2/M3 与 WAG MOVE/SWAP 都是跨机器人结构 |
| `joint4_core()` | FEASIBLE 走上式；DEADLOCK 仍走 Joint3B 的真实 blocked/blocker 核心；无接收方时回退 `select_routeaware_bottleneck`（q≤3） | 不推翻已验证的死锁机制 |
| `joint4_screen()` | 用现有 `priority_schedule()` 给每个完整候选打 native 值；只让排序后的前 2 个不同结构进入 B32 | 100 次 B32 要花在更有价值的候选上；HGA/WAG 也是 native 搜索期筛选 |
| `joint4_deadlock_signature()` | 死锁标识从“只 blocked parent IDs”扩展为 `(blocked 机器人, blocked 操作 kind/robot, blocked parents/blocks, blocker 操作 ID, blocker blocks, blocker parents 分组)` | 旧标识会把“父相同但 blocker 机器人/操作不同”的两个状态误判为同一核心 |
| `joint4_training_rank()` / `joint4_group_loss()` | 新标签：class 0 = `Pmax<=1.01*initial` 且 `spread<=max(0.5*initial_spread, 0.10*initial_Pmax)`；class 1 = 其它 FEASIBLE，**按连续负载质量 `max(Pmax/limit, spread/limit)` 再按真实 B32 Cmax 排序**；class 2 = DEADLOCK。pairwise loss 权重 = ΔCmax/ref + 0.25×Δquality | 旧标签 `spread<=initial+20` 比正式阈值松数倍；严格正样本稀疏时按要求用连续负载质量排序，而不是放宽正样本条件 |
| `joint4_fit()` | 用同一评分头（assignment+joint+insertion）在 20 个 TRAIN 实例上续训 3 epoch，初始化自 Joint3 权重 | 学“哪些父该迁出/哪个接收方/哪个组合值得换/哪种插入降低 MOVE/哪些会 WAIT 或死锁” |
| 核心规模回退阶梯 | q=4 的核心若无法完成重构（兄弟子段会被 canonicalize 合并），自动缩到 4→3，而不是丢掉整轮 | 5 父核心在部分排样上 8/8 完成全部被“canonicalization changed”拒绝 |
| `joint3_case` 恢复逻辑 | 断点续跑改为同时匹配 `phase` | 之前的续跑会跨 phase 误命中（消融实验暴露） |

没有改动：`gnn_constructor.py`、`hga.py`、`wag_vns.py`、B32、方向优化、负载阈值公式；没有新增网络、PPO、独立调度器/认证器/hash。

## 3. 核心规模 q 的证据与一处方法学披露

在 `validation_07`（1 个种子、40 次 B32、同一权重）上比较 q=3/4/5：

| q | 核心结构 | Cmax | 负载合格 |
|---|---|---|---|
| 3 | 2 转出 + 1 接收 | 6386.9 | 0 |
| **4** | **2 转出 + 2 接收** | **5884.2** | **1** |
| 5 | 3 转出 + 2 接收 | 6383.9 | 0 |

q=5 反而明显更差：去掉 5 个父后 beam 宽度 4 的重构更容易退化成坏解。**披露：这次 q 的选择是在 VALIDATION 排样上做的参数探查（4 个排样、1 个种子、40 次 B32），属于在验证集上选参数的方法学瑕疵**；第一阶段的 TRAIN 结果独立复算了 q=4，结论与该探查一致（见 §5），但该瑕疵不应被隐藏。

## 6. 改善究竟来自什么（三臂消融）

6 例 Cmax 中位：Joint3B **5246.5** → Joint4-unfit **5275.5** → Joint4 **5150.5**。

- **算子本身（新核心 + native 筛选、旧权重）没有带来 Cmax 收益**：Joint4-unfit 比 Joint3B 还差约 +0.6%（中位），说明只把核心从 3 父扩到“2 转出+2 接收”、并加 native 排序，不足以改善解质量。
- **收益来自标签改动**：同一算子换上按新标签续训的权重后，Cmax 中位比 Joint3B 低约 1.8%，比 unfit 低约 2.4%；Pmax/极差同步改善（极差 381→268）。
- 也就是说：**GNN 是否学会跨机器人分配，主要取决于训练标签教它“什么样的负载结构算好”，而不是核心多大**。这与本轮 §3 的核心目标一致，但也说明单靠扩大核心/加 native 筛选不会自动变好。

## 7. 失败与回退（不掩盖）

- **配对 Cmax 中位仅 -0.05%**（4 胜 2 负），不构成“明显改善”；最大回退 +1.45%（train_52），最大改善 -3.82%（scale_train_0973）。
- **死锁修复回退**：候选层死锁起点修复 67 → 37；死锁候选 129 → 150。原因是 Joint4 的轮次更多花在 4 父可行核心与 native 排序上，B32 预算里留给死锁起点修复的比例下降。这个方向需要在下一轮单独处理，不能假装没有发生。
- **MOVE 略增**（中位 590→619，+5%），WAIT 明显下降（7.6→0）。没有出现“用 MOVE/WAIT 暴涨换负载”的现象，但 MOVE 的增长需要在更大样本上复核。
- **运行时间**从 38.6s 增到 111.4s（native 评价 + 4 父重构 + 更多轮次）；在相同 B32 预算下这是额外成本。
- **与 HGA/WAG 的差距**：Joint3B 在 VALIDATION 上对 HGA 中位 +6.206%。第一阶段的 -0.05% 配对改善不足以改变这个结论，因此不进入 VALIDATION。

### 9.2 联合重构与单一优化目标

FEASIBLE 起点按真实最大完成时间确定关键机器人，以其加工、真实等待/阻塞、MOVE 弧端点及其他机器人完成时间裕量构成 2～4 机器人核心；主路径同轮移除 3～6 个完整父焊缝。接收集合来自现有合法模式/机器人目录，不固定一个接收机器人，不排除原 X 模式父任务的合法改模式机会。DEADLOCK 保留真实 blocked/blocker 核心及必要路线邻居；测量版本有3条2父例外，收尾已补下限检查，详见9.6。

原 vnext_joint_actions 同时选择合法模式、子段归属、插入机器人/位置、顺序和方向。宽度 8 的 beam 按父/模式/归属结构去重，并用机器人归属组合/流向差异保留多样性，避免被方向或插入顺序的重复状态占满。流向多样性是组合层面的启发式，不能保证最终包含真实焊缝转移的三/四机器人有向环；专项测试仅证明这些循环在同一解码器中可达，且保持原资格和 canonical 规则。是否实际产生有效循环，须以本次存储候选的几何转移明细统计为准。没有拼装 HGA/WAG 算子或独立方向器。

删除中间 Pmax 及预测负载的硬过滤。仅在完整候选的精确 LB=max_r(P_r+MOVE_r) >= 当前已测可行 Cmax 时剪枝；DEADLOCK 不提供 incumbent Cmax。新路径不使用 priority_schedule 的候选评价；每轮最多两个 GNN 候选进入原 B32，单例新增 B32 上限 100，外层上限 500、连续无新增评价上限沿用 128，无墙钟截断。

joint4_training_rank 对所有 FEASIBLE 直接按实测 Cmax 排序，DEADLOCK 为独立不可行类且 Cmax=None。joint4_group_loss 使用 Cmax 相对差配对 softplus（可行/不可行类别对保留原 0.25 权重），不使用负载质量。joint3b_select_final 和 incumbent_cmax 都不再要求负载合格，也不使用 1% 负载保持容差。Pmax、极差、MOVE、WAIT 只保留为输入和诊断。最终跨机器人变化按焊缝几何重叠长度计算，排除只改子任务名称、执行机器人未改变的情况，并计入切点变化造成的实际归属转移。

### 10.2 搜索与GNN的职责

- Relocate按父焊缝原子移除/重插；当前在来源机器人上的子段可迁往合法接收机器人，其余子段保持独立归属。合法WHOLE模式作为额外模式选择，不强制把拆分父焊缝绑定到同一机器人。
- Swap同时处理两个父焊缝及双方路线，方向随插入位置共同枚举。路线周期增量记录为四维route_delta_s，来源、目标及其他受影响路线全部重算。
- 2-opt在当前瓶颈路线反转片段并同时翻转相应焊接方向，作为一个完整动作评价，没有独立方向优化步骤。
- 三个局部邻域均无改进时，3～6父LNS扰动与相同动作评分网络修复；完整扰动允许暂时变差，保留全局最好原生可行方案，部分重建不做Pmax剪枝。
- 原生可行时关键机器人由当前完成时间和真实路线周期确定，原生失败时使用可观察的P+MOVE路线周期；每次接受后重新确定。接收次序依据当前完成时间裕量及合法目录，资格和X模式固定归属保持原规则。
- 原生FEASIBLE只按原生Cmax比较。原生DEADLOCK不赋虚构Cmax，保留为备选和周期性扰动分支；无原生可行方案时，GNN评分备选仍可进入唯一最终B32。
- 完整候选的max(P+MOVE)只用于安全排除无法改善当前原生可行Cmax的直接邻居，不作为加权替代目标；LNS扰动及原生DEADLOCK状态不受这个改进界限制。
- 完整方案还使用既有_initial_error检查B32原有初始位置/轨道顺序规则。这与scheduler.py的原输入检查相同，只对完整路线执行，不能用它冒充对native DEADLOCK的数学判定。
- 历史签名为普通模式/路线/方向元组。先去重和检查已知输入几何，再canonicalize、准备GNN特征或调用原生调度。缓存静态模式图、几何对应的路线表，保留不同模式及按子段顺序排列的机器人归属结构。提案与无GNN排序使用独立确定性随机流，避免排序随机数改变提案生成。

GNN保持原两层64维、4头及原assignment/joint/insertion头。每个当前搜索状态仅编码一次，Relocate/Swap/2-opt批量评分及LNS各部分重建共享该编码。图只使用当前已观察到的原生完成/WAIT与当前路线；没有真实blocked/blocker证据时不捏造8/9号边，没有把候选未来B32反馈写进在线输入。训练和推理的动作输入由同一适配函数生成。

阶段1/2先验证现有冻结模型及搜索机制，没有提前增加关系、GAT层数/头数、Cmax预测器、PPO/REINFORCE或新训练。更进一步的连续边属性/动作增量学习属于搜索有效后才允许开展的阶段3。

### 10.5 阶段3：固定小规模TRAIN学习设计

机制筛查通过后才接入连续属性，方法标识为GNN-BVNS-v2，继续使用同一已批准权重文件和CSV。文件内保留frozen_state_dict，原Joint3/Joint4/Cmax-Conflict文件不写入。两层64维、4头保持不变。

- 不增加关系类型，仍使用已有11种关系。对有向边增加六维连续属性：00/01/10/11四种焊接方向组合的实际空走时间、当前路线选定方向的转移时间、实际路线边标记。潜在几何冲突边、已知路线边、实际调度证据的关系类型保持分开。
- 当前节点增加关键机器人标记和可观察完成时间裕量。原生失败时只使用已知P+MOVE，并以动作中的原生状态位说明，不能填写未来B32信息。
- 原插入评分头增加32维输入：邻域类型、四机器人当前路线周期、完整动作四路线时间增量、当前完成时间裕量、关键机器人、真实转移父数及长度、未重建比例、原生状态、前驱/当前子焊缝/后继之间八个方向组合转移时间。中间重建的增量明确是部分路线状态，未假装成最终候选结果。
- 原线性层旧列及关系嵌入完整迁移，新增节点列、边到注意力投影及头输入列全部初始化为零。新输入在训练前不会扰动已有评分。仍只有原两个GAT层及assignment/joint/insertion评分头。
- 同一BottleneckActionScorer既收集/回放训练输入，又在线批量评分；每个当前状态仅编码一次，候选不另造整图。训练每次参数更新创建新评分上下文，避免使用更新前的缓存梯度图。

#### 具体失败环节与证据边界

1. **Cmax路线改善不足。** 23个可行最终方案中22个Cmax等于自身完整路线LB（误差1e-6s内），而对HGA为0胜23负。关键差距仍在归属/模式/路线联合决定的关键机器人周期，不能以降低总WAIT或负载极差来替代。发生了大量真实转移，不等于转移方向和路线组合足够好。
2. **原生可行性向B32的迁移失败。** validation_06种子10/11、validation_07全部三个种子、validation_10种子12共6例原生可行，最终B32仍DEADLOCK。训练中已有63个同类候选反例；当前图和排序学习没有消除这个偏差。没有放宽约束，也没有添加重复评价器为失败方案兜底。
3. **全原生失败状态下备选排序未修复。** validation_03种子12的500次原生评价全部DEADLOCK；访问8个状态、7次LNS失败分支，原生实际测了136条Relocate、168条Swap、168条2-opt及24条LNS（另4初解），最终GNN备选B32也失败，净转移父数为0。其他候选未额外用B32重筛，不能把原生失败解释成整个实例数学不可行。
4. **GNN增益缺少稳定证据。** 六例TRAIN对无GNN只有0.009253%的中位改善，正式新方法整体未达到质量目标。局部接受中2-opt 349次，Relocate/Swap合计127次；LNS接受含扰动且只累计85个转移父次。是否由根状态分布、候选覆盖或动作排序中的某项特征造成，本轮没有隔离消融，属于待验证原因，不能从这些计数直接作单一因果断言。

本轮代码实现事实是：同一个GNN批量评分合法父级邻域，动态图/连续有向转移属性和两端路线增量已接入，纯Cmax真实B32排序训练已执行，搜索中保留原生失败分支、最终B32只一次。实测结论是：统一BVNS显著降低了历史GNN运行成本，GNN对无GNN的TRAIN增益很小，官方VALIDATION的Cmax与可行性未过关。没有实测支持“超过HGA/WAG”。
