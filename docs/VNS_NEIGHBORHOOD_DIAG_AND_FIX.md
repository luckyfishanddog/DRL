# VNS 邻域诊断与修复实验报告

日期：2026-10-22  
运行环境：`D:\pybullet_test\.venv\Scripts\python.exe`  
求解 seed：`20261022`

## 1. 范围与结论

本轮只修改固定拆分问题下的 VNS 候选选择和统计，不修改 GNN、`gnn_constructor_v1.pt`、方向 DP、B32 调度器、独立认证器或任务可执行资格。所有接受的解均经过原方向优化、B32 和 certifier，并严格降低认证 Cmax。

结论属于任务给定的 **A 类**：原有邻域选择存在明显缺陷；修正后，VNS 已能有效改善任务分配和路线顺序。三个 20 秒 pilot 中，修复版对 RULE 和 GNN 初值均为 3/3 改善；六个 DEV 几何的 60 秒验证中均为 6/6 改善。

不过，60 秒下 GNN+VNS 的六实例平均最终 Cmax 仍比 RULE+VNS 高 1.37%。因此，本轮证明的是 VNS 已恢复优化能力，不是 GNN 已优于规则构造，也没有证据进入可选 Y/X 拆分的神经决策。

## 2. 根因

代码审查与真实邻域评价共同确认了以下问题：

1. 旧 N1 只为每次迁移保留目标路线局部代价最小的两个插入位置，再按源/目标两条路线的绝对最大代价取 Top12。它没有把未修改的另外两台机器人纳入系统最大负载判断。
2. 旧 N2 同样只按交换涉及的两条路线排序。结果经常把全部名额交给低代价机器人对，而不是当前关键负载机器人。
3. 旧 N3 按修改后单条路线的绝对代价排序，而不是按相对当前路线的改善量和系统最大路线代价排序。初始路线按 X 递增时，Top12 经常全部落在本来就便宜的非关键路线。
4. `run_vns()` 的“无改善则切换邻域、改善后回到 N1”逻辑没有原则性错误；错误在于被实际认证的 12 个邻居不能代表完整邻域。旧版在三个 pilot 上均提前结束，但扩大候选覆盖后存在大量被遗漏的认证改善。

典型集中现象：N35 GNN 的旧 N1 Top12 全是 R3→R2，旧 N2 全是 R2↔R3，旧 N3 全来自 R2；而真正关键的是负载 2885.70 s 的 R0。扩大诊断发现把 `inst0020|group=143-FR69B|row=0000::whole` 从 R0 迁移到 R1 后，认证 Cmax 可由 3065.20 s 降到 2787.76 s，旧 Top12 完全没有访问该方向。

## 3. 修改内容

修改文件：

- `src/mrta_search/vns.py`
  - N1/N2 使用四机器人整体最大加工负载、整体最大预计路线代价及相对变化作字典序排序。
  - N1 枚举合法插入位置；N2 保持固定任务集合并重新计算四机器人系统指标。
  - N3 使用系统最大路线代价、相对路线代价变化和关键路线信息排序，同时保留 2-opt 与重插入。
  - 排序末端使用同轨左右机器人 X 次序逆序数作为轻量协调提示；它不是硬可行性规则，也不替代 B32/certifier。
  - 每个邻域保留少量不同迁移方向、交换机器人对、机器人/重排类型，避免全部名额集中在同一操作类型。
  - 保留 `LEGACY_LOCAL_ABSOLUTE` 选择策略，仅用于配对复现实验；默认使用 `GLOBAL_BALANCED`。
  - 增加合法唯一邻居数、实际探索操作类型、认证数和失败数统计。
  - 支持注入同一个已认证初值，使 legacy/fixed 配对不受初始化修复差异影响。
- `scripts/run_gnn_construct_vns_pilot.py`
  - 增加 `--vns-fix-mode`，跳过训练并从同一个认证初值运行 legacy/fixed 配对。
  - 输出初始/最终负载、空走、等待、邻域评价、认证失败、任务归属变化和路线变化。
- `tests/test_gnn_construct_vns.py`
  - 增加关键机器人 N1/N2 选择、N3 相对改善排序、全候选覆盖合法性、候选去重、严格认证接受和可复现性检查。

没有加入扰动或 `SAME_RAIL_JOINT_ADJUST`。修正 N1/N2/N3 后已经找到并在线兑现有效改善，当前证据不足以证明必须增加第四个领域算子。

## 7. 改善来源与未解决问题

- N35/N55 的主要收益来自 N1：关键机器人任务被迁移后，最大加工负载显著下降；N2 的有效贡献较少，但在 RULE 两个几何和 GNN 两个几何上仍产生严格改善。
- N3 在 60 秒 RULE/GNN 中分别产生 17/13 次改善，是最稳定的邻域。N86 的任务归属完全不变，收益来自路线顺序、空走和等待变化，证明 N3 不只是重复已有 X 递增路线。
- N82 的搜索时间主要被 N1 用完，尚未进入或充分进入 N2/N3；它仍通过任务迁移获得 6.78%/18.46% 改善。候选完整构造与真实调度评价在大实例上仍是主要时间开销。
- 修复后的探索覆盖更广也产生更多 DEADLOCK；这不是接受了不合法解。所有最终解均为已认证全局 best，失败候选只计数不接受。
- 没有证据需要立即增加同轨联合邻域：当前三个邻域已在所有六个几何上产生改善。若后续专门研究 N86 类路线协调，可再以成对同轨路线重排的反例为前提验证，而不是现在增加算子。

## 9. 是否继续修改 GNN

VNS 已能稳定改善 GNN 初值，但 GNN 初值的负载失衡仍明显，且相同 VNS 后总体没有超过 RULE。下一步若继续 GNN，应先用修复后的 VNS 生成质量更好的固定拆分教师，并重新检查共享区任务归属；不应增加网络层、第二个评分器或候选筛选器。

当前没有证据研究可选 Y/X 拆分的神经决策。应先要求固定拆分下 GNN+VNS 至少稳定达到或超过 RULE+VNS，再扩大决策空间。
