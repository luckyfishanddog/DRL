## 1. 修改了哪些核心代码

| 位置 | 改动 | 为什么 |
|---|---|---|
| `joint3b_pool()` | 新的六类搜索池：负载合格最小 Cmax、最小 Cmax、最佳负载均衡、最佳死锁进展、**阻塞父集合不同的第二个死锁**、最新状态；某类缺失时用其它有效候选补齐；仍用 `plan_key()` 去重 | 旧池 6 个位置里可行方案类别占 4 个、死锁只有 1 个；死锁修复缺少可继续重构的状态，且同一死锁会被反复处理 |
| `joint3b_deadlock_choice()` | DEADLOCK 核心改为**先按 B32 实际 blocked/blocker 覆盖度排序**（覆盖的 blocked∪blocker 父数、blocked 父数），GNN assignment logit 只做同覆盖度内的次序；必要邻居只从 blocked MOVE 端点两侧取 | 旧实现按 GNN 平均 logit 选核心，可能挑到与真实阻塞无关的父；邻居从所有核心父 ±1/±2 扩，会无理由扩大范围 |
| `joint3b_core()` | FEASIBLE 仍复用 `lns.select_routeaware_bottleneck()`；DEADLOCK 走上面的证据排序 | 保持唯一核心算子，不新增选择器 |
| `joint3b_select_final()` | 同时保留 `best_balanced_feasible` / `best_cmax_feasible` / `best_balance_feasible`，计算 `R_C=(Cmax_balanced-Cmax_best)/Cmax_best`，按 1.0% 容差取舍 | 不再让 `load_allowed` 单独决定最终方案；也不允许为负载无条件牺牲 Cmax |
| `joint3b_failure_final()` | 预算耗尽仍无 FEASIBLE 时写 `status=NO_FEASIBLE_SOLUTION`、`cmax_s=None`，保留最佳死锁的阻塞证据 | 最终死锁保护：绝不能把 DEADLOCK 伪装成成功 |
| `joint3_case(variant='joint3b')` | 死锁起点重构时在池内**扫描未展开过的 (状态, 核心)**，避免同一死锁被重复重建；统计 `deadlock_origins`/`deadlock_repairs` | 旧实现每轮只取池指针指向的单个状态，核心已展开就计 stale，导致预算没用完就停 |
| `joint3b_relative_limits()` | TRAIN 阶段用 `Pmax<=1.01*初始Pmax`、`spread<=初始极差+20s` 的相对保护（沿用原训练标签规则） | TRAIN 没有 HGA/WAG 冻结参考；两个版本用同一把尺子，比较才公平 |
| `joint3_case` 计数修复 | 去掉 `entries` 的重复 append（候选被 `evaluate` 和 `extend` 各计一次） | 上一阶段报告里的「4306 个候选」是重复计数，真实为 **2168**（2168 行 = 30 initial + 2138 candidate）；本轮所有统计改为按 CSV 行计数 |

没有改动：`gnn_constructor.py`、`hga.py`、`wag_vns.py`、B32 调度器、方向优化、负载阈值公式；没有新增网络、独立认证或哈希框架。

## 2. 负载与 Cmax 的取舍规则（先定规则，再看结果）

三个状态与 `R_C`：

- `best_balanced_feasible`：满足现有负载范围（严格口径：`Pmax<=1.05*max(HGA,WAG)`、`spread<=max(参考极差, 0.1*峰值中位)`）且 B32 可行的最小 Cmax。
- `best_cmax_feasible`：所有 B32 可行方案的最小 Cmax。
- `best_balance_feasible`：所有 B32 可行方案中 `max(Pmax/limit, spread/limit)` 最小者。
- 取舍：若存在 `best_balanced_feasible` 且 `R_C<=1.0%`，最终取它；否则取 `best_cmax_feasible`（并如实把 `load_allowed=0` 写出）。阈值公式本身**没有任何改动**。

TRAIN 上的 0.5% / 1.0% 容许差距（只用 TRAIN，不用 VALIDATION/TEST 标签）：6 个 TRAIN 排样里 **5/6 的 R_C<=0.5%，5/6 <=1.0%，1 个为 10.74%**（`scale_train_0617`：保持负载要付 10.7% 的 Cmax，按规则选 Cmax 最优）。因此主口径取 **1.0%**：它保留全部「负载代价很小」的合格解，只拒绝明显不划算的那一个。

VALIDATION 上（仅报告，不用于调参）：12 个存在负载合格候选的案例中，`R_C` 中位 0.0%、最大 0.73%，**11 个 <=0.5%、12 个 <=1.0%、0 个 >1.0%**。也就是说：只要搜索能找到负载合格候选，保持负载几乎不花 Cmax；负载合格率上不去的瓶颈不是取舍规则。

## 3. 死锁修复改动与第一阶段（TRAIN）

死锁核心的证据排序（新）：

1. 从 `schedule.deadlock_blockages` 收集每个 `(blocked parent IDs, blocker operation, blocker parent IDs)` 组；
2. 先按 `|blocked ∪ blocker|`、再按 `|blocked|` 排序，GNN assignment logit 只在同覆盖度内决定先后；
3. 核心 = 该组的 blocked ∪ blocker 父；必要邻居**只**从 `blocked_block_ids`（真实阻塞 MOVE 端点）在路线中的左右相邻块取，且总数不超过 `max(3, |core|)`；
4. 之后仍然走原 `joint3_reconstruct()`（同一 GNN 联合动作决定模式/归属/插入位置顺序/方向），不新增方向阶段。

## 5. 五个问题的直接回答

1. **最终死锁是否为 0**：是。30/30 FEASIBLE，`final_choice` 全部为 `balanced`/`cmax`，没有 `NO_FEASIBLE_SOLUTION`。搜索中仍有 766 个 DEADLOCK 候选（33.4%），但都被池当作修复起点，未进入最终输出。
2. **负载合格率**：12/30 vs 13/30，没有提高。根因有数据支撑：Joint3 也只有 13 个案例（64 个候选）出现过负载合格可行解，J3B 是 12 个案例（55 个候选）——**18/30 的案例在整个搜索里从未出现负载合格可行解**。三父局部邻域无法把 10 个排样的极差从 691~3454s 压到参考水平（86~1177s）。缺的不是阈值，是能产生均衡解的移动。
3. **Cmax 是否被负载均衡拖累**：没有系统性拖累（中位 0.0%，12 胜 10 负）。真正的原因是搜索路径差异：J3B 把更多预算花在死锁起点（891 次 vs 652 次），部分案例因此找到更好的协调路线（validation_10/1110 -9.87%、validation_06/1112 -5.45%），部分案例反而错过 Joint3 的好解（validation_03/1110 +4.13%、validation_08/1110 +3.50%）。这是「死锁修复优先」的代价，不是负载约束造成的。
4. **MOVE/WAIT 是否不合理增长**：没有系统性增长。30 例中位 WAIT 56.6s → 37.0s、MOVE 605.7s → 610.8s（+0.8%）；个别案例以 WAIT 换 MOVE（如 validation_06/1110：MOVE 610.9→535.0、WAIT 0→128.0，Cmax 反而 -0.59%），也有反向（validation_07/1112：WAIT 433.4→33.0、MOVE 681.2→610.0）。没有出现「负载更好但 MOVE/WAIT 暴涨」的系统现象。
5. **死锁修复是否真的改变归属/路线**：是。死锁起点重构的成功率 44.0% → 61.4%，且成功修复中 99.5% 带有模式或机器人归属变化（Joint3 为 96.9%）；证据排序让核心更贴近真实 blocked/blocker 父，必要邻居只从阻塞 MOVE 端点扩。

## 6. 失败与回归（不掩盖）

- **负载合格率没有提高（12/30 < 13/30）**：新规则没有放宽阈值；下降来自 6 个案例失去合格解、5 个案例新增合格解、净 -1。典型：validation_03/20261110 从 5274.0（合格）变成 5491.8（不合格），validation_10/20261110 反向从 6188.9（不合格）变成 5578.4（合格）。
- **Cmax 有 10 个案例回退**，最大 +4.13%（validation_03/20261110）、+3.94%（validation_05/20261112）、+3.65%（validation_07/20261112）、+3.50%（validation_08/20261110）。这些案例中 J3B 的死锁起点重构更多，预算被从「可行瓶颈重构」挤走。没有证据表明是负载取舍造成的（这些案例的 `choice` 都是 `cmax`，即根本没有负载合格候选）。
- **与 HGA/WAG 的差距没有缩小**：+6.21% / +5.10%（上一阶段 +6.63% / +4.96%），HGA 仍是 0 胜。三父局部重构 + 100 次 B32 的搜索强度不足以弥补与 200000 次迭代 HGA 的差距。
- **训练标签与正式阈值不一致**（§2 表）：本轮按要求不重训；下一阶段若重训，应把 class 0 改成极差主导，否则学到的「负载合格」仍偏松。

## 7. 对上一阶段报告的两处勘误

- 「4306 个候选」是 `len(entries)` 的重复计数（每个候选被 `evaluate` 与 `entries.extend` 各计一次），真实为 **2168**（30 initial + 2138 candidate）；本轮已修代码，所有统计按 CSV 行计数。
- 上一阶段报告 §9 的示例「validation_04：初始 Pmax 5927 vs 上限 5124」用的是**训练前**构造。训练后同一排样初始构造为 Pmax 5029.2 / 极差 1623.4，仍不合格（极差超上限 1048.2），结论不变，但数值以本报告 §2 表为准。
